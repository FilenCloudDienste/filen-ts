# Assistant

An AI assistant that runs entirely on the user's device. A small open-weights model (GGUF, run by [wllama](https://github.com/ngxson/wllama), llama.cpp compiled to wasm) answers questions about the user's drive, notes, chats, photos and music, navigates the app, and drafts chat messages. Nothing the user asks or the assistant reads leaves the device.

Paths starting with `packages/` are from the repo root, `src/`, `vite/` and `scripts/` from `packages/filen-web`, the rest from this directory.

## Hard rules

- **On-device only.** No inference service, no telemetry. The only new network traffic is the model download from the Filen CDN; tools read data through the app's usual end-to-end encrypted requests and caches.
- **Opt-in.** Nothing is downloaded until the user clicks Download in the panel. The model loads into memory only on an explicit request (a sent message or the Load action), never because the panel opened.
- **Nothing is ever permanently deleted.** No tool can delete permanently, empty the trash, unshare, leave, change links or touch the account. Removal can only mean the restorable trash, and only after a confirmation.
- **Read and navigate, plus confirmed drafts.** The web app runs read, navigation and `draft_chat_message` tools (`ASSISTANT_WEB_TOOLS`). A draft only fills the chat composer; the user still presses Send. The shared registry already defines writes (move, rename, trash, ...); the web app does not offer them yet.
- **Safety is enforced in code, never by the model.** Text other people write (shared item names, note and file contents, chat messages) can steer the model, so:
    - _scope_: the router reads only the user's own words and picks one tool group plus read/change; a turn can call only that group's tools (the model is shown those of the group's whole prompt family, the loop refuses the rest) and a read turn never gets consequential tools;
    - _grounding_: a consequential call's handles must trace back to the user (the screen context, a lookup the user asked for, a name the user typed); new names, recipients and destinations must appear in the user's own message;
    - _taint_: once a turn has read other people's content, consequential tools and `open_route` are withdrawn for that turn;
    - _sanitize / quarantine_: untrusted strings lose chat-template control tokens (including the loaded model's own special tokens, read from the GGUF header) and invisible/bidi characters (the joiners a word's or an emoji's spelling needs stay, and link checks read past them); note bodies, file text and chat messages are summarized by a tool-less extraction call before the main loop sees them;
    - _reply screen_: links and addresses the user did not type are defanged, a reply that echoes the system prompt (its per-conversation canary or an instruction line) is withheld, and replies render as markdown with no live links or images;
    - _confirmation_: a consequential call runs only from a confirmation card clicked by a trusted, browser-dispatched event (`components/userActivation.ts`), never from script or the model;
    - _import ban_: [`eslint.config.js`](../../../eslint.config.js) forbids `src/features/assistant/**` and the worker from importing irreversible or security-critical operations, the raw SDK, settings/auth modules, and any dynamic `import()`. [`src/tests/assistantImportRestrictions.test.ts`](../../tests/assistantImportRestrictions.test.ts) pins the rule.

## Model lifecycle

- **Device check** (`deviceCheck.ts`): desktop browsers with wasm SIMD, exceptions, Memory64 and OPFS, and at least `MIN_DEVICE_MEMORY_GIB` where the browser reports memory. WebGPU when JSPI is present, the adapter can bind 1 GiB buffers and the browser is not Firefox; otherwise the CPU path, which needs cross-origin isolation and at least 2 threads (half the cores, at most 8). Mobile browsers are refused, including an iPad that sends a Mac's user agent (it reports touch points). A failed WebGPU load falls back to the CPU path in a fresh worker; only once that loads does the page stay on the CPU path.
- **Download**: shards are fetched 3 at a time, largest first, hashed as they arrive (a hasher checkpoint beside each partial shard), resumed with `Range` after stalls, errors, reloads or crashes, and recorded in `verified.json` only once their sha256 matches the pinned manifest. A download without room for the rest of the model is refused (`navigator.storage.estimate()`), and persistent storage is requested from the click.
- **Explicit load, idle unload**: the worker exists only while downloading or running; terminating it frees the engine's memory and GPU device. The model unloads after `IDLE_UNLOAD_MS` without activity (wall clock, also re-checked on visibility change), panel open or not. An unanswered card expires after `CARD_EXPIRY_MS` so it cannot pin the model; its expiry counts as no activity, so the model unloads on the user's own deadline. Stop waits for the engine to wind down at least `STOP_WATCHDOG_MS` and three times its slowest prompt batch (from the load's priming until a turn has timed one) before the worker counts as stuck and is replaced. A confirmed action runs to its end even after Stop or a new conversation; only sign-out stops it.
- **Earlier model versions**: another model in OPFS is an earlier version only while the server still deploys this build (`index.html` loads this bundle); from a replaced build it may be a newer tab's, so this tab updates instead and touches nothing. An earlier version's bytes count as room for this one, and it is removed, under the lock, only once a download starts; before that, the panel's Remove frees it (`staleBytes`). Remove from a build the server is not known to deploy deletes only this build's model.
- **One tab**: the Web Lock `filen-assistant-model` is held while a tab downloads or runs the model. Other tabs show it as in use elsewhere and re-check when the lock is released, so OPFS is never written by two contexts.
- **Forced calls**: the loop makes the first step of a lookup (a read request outside music and navigation, whose read requests mostly act) call one of the tools that read (over a long conversation the model otherwise answered new lookups from earlier replies, making up what a call would have read). A forced step that calls nothing, or anything but those tools, is written again unforced, so an action or a plain reply is never forced. Such a request (`toolChoice: "required"`) gets llama.cpp's `tool_choice: "required"`, and, for a template that opens calls with `<tool_call>`, the reply starts with that opener as a trailing assistant message, which the engine continues. `required` alone only forbids ending without a call, so the model still wrote its made-up answer first and called after it.
- **Router prompt priming**: the router's system prompt is fixed. At load the worker reads it once in the model's ChatML layout, so every router request reads only the user's message; after a turn it is read again if a request found it evicted (`reprime`). Priming applies only to ChatML templates.
- **Cache sizing**: one unified KV cache of `ASSISTANT_CONTEXT_TOKENS + ROUTER_CONTEXT_TOKENS + QUARANTINE_CONTEXT_TOKENS` with 3 slots (router, main loop, extraction), idle-slot caching off, and context checkpoints per slot (6 on WebGPU, 4 on the CPU path, whose 4 GiB of wasm memory also holds the weights) with a minimum step of 256 tokens. Qwen3.5 is a hybrid model that resumes a cached prompt only from a stored state checkpoint. A request stores up to two near the end of its prompt; once a slot's list is nearly full, the engine drops earlier requests' checkpoints within the step of an older kept one, then the oldest. At the default step (8192 tokens) little but the oldest survives, so a turn resumes far back; with too few, a turn of several tool steps with long results evicts the one the next turn resumes from, and that turn reads its whole prompt again. The host-memory prompt cache, where a slot's prompt goes when another prompt takes the slot, is sized per backend (`PROMPT_CACHE_MIB`): 2 GiB on WebGPU, where at the engine's default of 8 GiB, twice what the wasm heap can grow to, a long session ended in `std::bad_alloc`; off on the CPU path, whose heap also holds the weights, KV cache and checkpoints (3.6 GiB once loaded): a slot's prompt, 160 to 320 MiB with its checkpoints, failed to allocate on the fourth turn, and the engine copies the checkpoints without guarding that allocation. [`patches/@wllama__wllama@3.8.1.patch`](../../../../../patches/@wllama__wllama@3.8.1.patch) passes `n_ctx_checkpoints`, `checkpoint_min_step` and `cache_ram_mib` through to the engine; the last needs the engine built below. Keep prompts prefix-stable: every main request renders the tools of its group's prompt family (`ASSISTANT_PROMPT_FAMILIES`: drive/trash/sharing, organize, insights, notes/chats, music/navigation) in one fixed order, so a route change within a family reuses the prompt (the chat template puts the tools first; a per-group list made every route change read the whole conversation again), and a return to an earlier family resumes the copy the engine moved to its host-memory prompt cache when another family took the slot. The answer route renders no tools (shown tools it may not call, the model tries them and answers worse). The system prompt changes only with the family (its unavailable-tools line), per-turn data (date, screen context, and the names of the tools this request may call when the family shows more) goes in the user turn, and conversation history only grows within its budget before it is cut back to half. What a request may call is enforced by the loop and the guard, never by what the model is shown.

## The engine build

The worker loads `src/vendor/wllama/wllama.wasm`, not the npm package's: wllama's glue code has no way to set llama.cpp's prompt cache limit, and loading the weights left large buffers behind, so [`scripts/wllama/build-wllama.sh`](../../../scripts/wllama/build-wllama.sh) rebuilds the engine of the pinned wllama release with [`scripts/wllama/glue.patch`](../../../scripts/wllama/glue.patch), which appends `cache_ram_mib` to the load request and changes how the weights are read and written to the GPU (see Memory below). The package's JavaScript stays in use (the pnpm patch adds the field to its message prototype), and the emscripten glue it embeds is byte for byte what this build emits, so only the `.wasm` changes. The load request is positional: the patched prototype must list the C++ struct's fields in the same order, which `src/tests/wllamaEngine.test.ts` checks against the package's `cpp/glue.hpp` plus the patch.

- **Memory**: right after loading Qwen3.5-4B on WebGPU, Chrome's page process held ~2.5 GiB and its GPU process ~3.9 GiB (`footprint`, memory-infra traces and the wasm heap size). Of the page's: the wasm heap, ~1.2 GiB, held the 497 MiB token embeddings llama.cpp keeps on the CPU (the GPU holds its own copy for the tied output weights) and the freed ~500 MiB buffer the output weights were staged through, which a wasm heap never gives back; ~500 MiB was the JavaScript buffer of the last file read (the embeddings, read in one request and still referenced in wllama's worker); ~620 MiB was shared memory Chrome allocates for GPU buffer writes of 4 MiB or more and then keeps, counted again in the GPU process. The patch stages a tensor in 16 MiB pieces, so neither the heap nor that shared memory grows to the largest tensor, and requests file reads in 16 MiB pieces. Interleaved, 7 loads each: page 2539 → 1064 MiB and GPU process 3909 → 3316 MiB after loading (medians), load 26.5 s both (21.7–38.0 and 21.8–27.5 s); after a conversation 1.5 GiB less in the page and 0.6 GiB less in the GPU process, with every reply the same and turns as fast. On the CPU path (3 loads each) nothing changes but the reads: the weights live in the heap, the page holds ~3.6 GiB either way, load 128 → 120 s (medians, machine busy), same reply. Splitting GPU buffer writes below 4 MiB on top of this saved nothing more and made loads about 1–2 s slower. The heap is ~1.25 GiB after loading, 50 MiB more than before, which a session takes up anyway (both reach the same size after a conversation or an eval pass): besides the embeddings, ~300 MiB is the worst-case split buffer of llama.cpp's scheduler (`ggml_backend_sched_new`'s context buffer, sized by the graph's node limit), reserved but barely touched, so it costs room under the 4 GiB heap limit, not memory, and ~140 MiB is the primed system prompt. A session's prompt cache grows the heap further, up to `PROMPT_CACHE_MIB`.
- **Why a committed binary**: it is 8.8 MB (2.4 MB gzipped), changes only with a wllama update, and keeps installs and CI free of a 2 GB toolchain; pnpm patches cannot carry binaries, and a CI build would make every build depend on that toolchain and on GitHub downloads. Vite emits it as a hashed asset like the package's file before it, served same-origin under the existing CSP (`'wasm-unsafe-eval'`) and COOP/COEP headers; the service worker does not cache assets.
- **Recipe**: the one wllama publishes with (its `scripts/build_wasm.sh` in the emscripten/emsdk image): wllama and its llama.cpp submodule by commit, Emscripten 4.0.20 through emsdk, Dawn's `emdawnwebgpu_pkg` release checked against its SHA-256, `-DGGML_WEBGPU=ON -DGGML_WEBGPU_JSPI=ON` and `-ffile-prefix-map=<source>=/source`. Each run first builds the release unpatched and compares it with the npm package's `wllama.wasm`, then applies the patch, which recompiles only the files it changes. `src/vendor/wllama/manifest.json` records the inputs, the hashes of the script and patch, the license files copied beside the binary, and the output's size and SHA-256.
- **Rebuild**: `scripts/wllama/build-wllama.sh` writes the binary, licenses and manifest. It needs git, curl, shasum, unzip, python3, cmake and make, and installs emsdk at the 4.0.20 tag's commit (about 2 GB) into a temporary work directory; set `WLLAMA_WORKDIR` to a directory of its own to keep emsdk, sources and downloads between runs. A run takes a few minutes. Then regenerate the third-party notices (`scripts/generateThirdPartyNotices.ts`), which read the manifest.
- **Check the binary**: `scripts/wllama/build-wllama.sh --check` rebuilds and requires the committed file byte for byte, writing nothing; `src/tests/wllamaEngine.test.ts` checks the committed binary, licenses, script and patch against the manifest on every test run. The toolchain is checked by the versions its tools print and, end to end, by the unpatched build, which must be npm's file byte for byte. Emscripten 4.0.20's LLVM orders the try blocks of a function in `llama-kv-cache.cpp` by memory address ([llvm/llvm-project#204883](https://github.com/llvm/llvm-project/issues/204883), fixed after that release): recompiled on its own, it nested them as npm's build does 27 times in 36, while its first compile inside the parallel full build did so in only 1 run of 5, so most runs take two or three attempts. The unpatched stage recompiles that file until the module matches npm's (up to `WLLAMA_ATTEMPTS`, default 10), and stops without output if it never does; the patched build then comes out the same on every run (the patched `cpp/wllama.cpp` compiled the same 20 times out of 20, and the patched module, with `llama-model-loader.cpp` recompiled too, came out the same in 4 builds of 4; `ggml-webgpu.cpp` compiles differently in another build directory without changing the module).
- **Update wllama**: bump the package, set the commits, Emscripten release (emsdk's tag commit and the versions its tools print), Dawn package and npm hash at the top of the script from the new release, rebase `glue.patch` and the pnpm patch (field order!), build, regenerate the notices, and measure in the browser before shipping.

## Adding or changing a tool

1. **Define it** in `packages/filen-shared/src/assistant/tools.ts` with `defineTool`: a snake_case name, a `title` (named in the prompt while the app cannot run the tool), a description the model reads, its home `group`, an `input` of arguments in the order the model reads them, each an arktype `type` with its `description` and `optional` flag (an enum through `oneOf`, which keeps its values' order) inside the portable subset (string, integer, boolean, enum, scalar arrays; every property described; no nesting, unions, floats, bounds, formats, patterns or defaults), and the guard metadata: `effect` (`read`/`navigate`/`additive`/`modifying`), `untrustedOutput` (`none`/`names`/`content`), `exfiltrates`, and `grounded` (which arguments are handles, free text or link-bearing text). `additive`, `modifying` and `exfiltrates` make it consequential. Take items by handle, never by UUID; take dates as `period`/`from`/`to` and resolve them with `dates.ts`.
2. **Route it**: add it to `ASSISTANT_TOOLS` and to one or more groups in `ASSISTANT_TOOL_GROUPS` (at most 6 tools per group, the home group included; update the group description if the router must learn new phrasing). Add it to `ASSISTANT_WEB_TOOLS` once the web app runs it.
3. **Shared tests** (`packages/filen-shared/src/tests/assistantTools.test.ts`) lint every schema, enforce the group size, and pin the lists of modifying, consequential, exfiltrating and content-returning tools; change those pins deliberately.
4. **Web adapter**: write it in `tools/<area>.ts` and register it in `ADAPTERS` (`tools/executor.ts`, typed so a missing web tool fails typecheck). Every list of items (records with a `handle`; not `transfers`, whose rows gain one only once their item exists) reaches the model as one line per item (`f3 ⟦CV.pdf⟧ in=⟦/Documents⟧ size=1.2 MB`, `serializeToolResult`), and prompt tokens are most of a step's wait in the browser, so a row carries only what the model needs: `handle`, `name` or `title`, then few fields. A long listing pages with `listingPage`: `offset` in, `more` and `next` (the following page's offset) out, and, past three pages, `shown` (`1–30 of 214 items`: a bare total was passed as the next offset, and on a short listing a count made the model answer a follow-up from it instead of paging); a list cut at a limit without paging adds `listRest` (`total` and `more`), so the model copies a count instead of adding numbers up. Register every item the result names through the scope (`show`) so the guard and handles know it, report long work through `progress`, honour the signal, and go through the feature modules the user's own actions use (the ESLint ban keeps the raw SDK out). Add the step label to `TOOL_ACTIVITY_KEYS` (`components/assistant.logic.ts`) and `src/locales/en/assistant.ts`. A consequential tool also needs a card in `loop/executorAdapter.ts`; without one it cannot run.
5. **Eval**: implement it in `packages/filen-assistant-eval/src/fakeApp.ts` (data in `fixture.ts`), add cases under `src/cases/` in several languages, injection cases if it returns other people's text, and run the gate below.

## Development

- `pnpm run dev` serves the assistant against the production model from the CDN unless configured otherwise.
- `VITE_ASSISTANT_MODEL_BASE_URL` points a build at another directory of model files (https, or http on localhost). `vite.config.ts` adds its origin to `connect-src`. The pinned manifest still applies, so the host must serve exactly the pinned files.
- `FILEN_ASSISTANT_DEV_GGUF=/abs/path/model.gguf pnpm run dev` (or the first piece of a split model) serves a local model through the dev-only plugin in [`vite/assistant-model.ts`](../../../vite/assistant-model.ts) under `/__assistant-model/`, with a manifest hashed on first request. It applies only in dev builds without `VITE_ASSISTANT_MODEL_BASE_URL`. A download removes other models from OPFS before it starts, so switching between dev and shipped models downloads again.

## Hosting and updating the model

- **Host constraints** (`cdn.filen.io/gguf/`): only CORS-simple requests work (the host answers `OPTIONS` with 405), so the download sends no header except a single `Range: bytes=N-`, with `credentials: "omit"` and `cache: "no-store"`. `Content-Range` is not exposed; a resumed response is recognized by status 206 and `Content-Length`. The host must send `Access-Control-Allow-Origin` and honour `Range`.
- **Split** the upstream GGUF with llama.cpp's `llama-gguf-split --split-max-size 512M <model>.gguf <prefix>`, which writes `<prefix>-0000N-of-0000M.gguf`. wllama cannot load a file over 2 GB without JSPI, and smaller pieces resume and verify independently. Publish the pieces (and, for runtimes without that limit, the unsplit file) under new names; never overwrite a published file, since deployed builds pin its hash.
- **Pin** the files: `pnpm exec tsx scripts/assistant-model-manifest.ts /path/to/<prefix>-00001-of-0000M.gguf` prints the `shards` list (sizes and sha256) for a new manifest in `runtime/models.ts` with a new `id`; run it on the unsplit file for the optional `whole` entry. `parseManifest` rejects pieces out of llama-gguf-split order or over 2 GB.
- **CSP**: the default host is inside `connect-src`'s `https://*.filen.io`; any other host needs `VITE_ASSISTANT_MODEL_BASE_URL` at build time (see above).
- A different model family also needs its chat template, tool-call format, thinking mode and special tokens checked in the worker (priming assumes ChatML) and a full eval run.

## Eval gate

Every model-facing change (prompts, tool definitions or descriptions, groups, guard, sanitizing, context or history layout, the model or its settings) is measured with [`packages/filen-assistant-eval`](../../../../filen-assistant-eval/README.md), which runs this exact shared loop on a fake app. Run it before and after on the shipped model with `--presets shipped,loop`: no regression in pass rate or routing, and 0 executed / 0 leaked on the injection suite for both presets (`shipped` refuses unsupported writes before the guard, so only `loop` tests the guard on them). Add cases for the new behaviour.
